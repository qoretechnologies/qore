## Status

Draft — open for review.  No implementation yet.

## Motivation

Programs that depend on modules outside the standard search path
(`/usr/{lib,share}/qore-modules/...`) currently have two options:

1. **Set `QORE_MODULE_DIR`** in the environment before invoking
   `qore` / the compiled binary.  Pushes deployment knowledge into
   the launcher (shell wrapper, systemd unit, cron config, …) and
   couples every consumer of the script to that knowledge.

2. **Embed the module path setup in C++** alongside libqore — what
   Qorus does today via `qorus_setup_module_paths()` in
   `exec/qorus_lib.cpp`:

   ```cpp
   void qorus_setup_module_paths(const char* argv0) {
       const char* dir = getenv("OMQ_DIR");
       // ... derive path from argv0 if OMQ_DIR unset ...
       MM.addModuleDir("$OMQ_DIR/lib/modules");
       MM.addModuleDir("$OMQ_DIR/qlib");
       MM.addModuleDir("$OMQ_DIR/user/modules");
   }
   ```

   Works for **source-embedded binaries** (the legacy Qorus build
   compiles its `.qo` files into the same ELF as `qorus_lib.cpp`).
   Does NOT work for **AOT-compiled binaries**: `qcc -m`, the cmake
   `qore_user_module()` macro with `QORE_BUILD_AOT_MODULES=ON`, and
   the AOT-compiled-script path (`qore -b --compile`) all produce
   binaries whose host code is generated by libqore — there is no
   user-editable `main()` to call `MM.addModuleDir()` from.

   The result, as observed in this repository: when Qorus binaries
   move to AOT, every Qorus deployment must remember to set
   `QORE_MODULE_DIR` correctly before launch, OR Qorus must keep a
   parallel "setup" entrypoint per binary just to register paths
   before transferring to the AOT-compiled body.  Both are fragile.

## Proposal

Two new parse directives that prepend / append a directory to the
module search path **declaratively from inside the source program**:

```
%prepend-module-path "<path>"
%append-module-path  "<path>"
```

The `<path>` argument is a quoted string that may contain
**variable references** of the form `${NAME}`, expanded at parse time
against:

- a small fixed set of **Qore-defined macros** (see
  [Predefined macros](#predefined-macros) below), AND
- the **process environment** (everything else).

Both names share a namespace; macros take precedence on conflict.
Unknown / unset names cause a parse error rather than silent
empty-string substitution — silent expansion has historically
produced bind-mounted `/qlib` paths and similar foot-shooting.

### Examples

```qore
# Qorus binaries — replaces qorus_setup_module_paths() entirely.
%prepend-module-path "${OMQ_DIR}/qlib"
%prepend-module-path "${OMQ_DIR}/user/modules"
%prepend-module-path "${OMQ_DIR}/lib/modules"
%requires QorusInterfaceCore
%requires QorusClientBase
```

```qore
# Self-contained vendored modules next to the script.
%prepend-module-path "${SCRIPT_DIR}/qlib"
%requires MyVendoredHelper
```

```qore
# Append a fallback location (system path takes precedence).
%append-module-path "${HOME}/.qore-modules-fallback"
%requires SomeFallback
```

## Semantics

### Order of effect

The directive takes effect **immediately at parse time**, before any
`%requires` that follows it on later source lines.  A `%prepend` or
`%append` placed AFTER a `%requires` has no effect on that earlier
load (which already resolved against the prior search path) but does
affect every subsequent `%requires`.

This matches the existing precedent set by `%new-style`, `%require-types`,
`%try-module`, etc.: parse directives apply to source from the line
they appear on, forward.

### Search-path layering

The effective module search path at any point during parse is, in
order of precedence (highest → lowest):

1. **Per-Program `prepended` paths** (most-recently-added first;
   each `%prepend-module-path` puts itself at the head)
2. **Process `QORE_MODULE_DIR`** entries
3. **Compiled-in default module paths**
   (`${PREFIX}/share/qore-modules/<ver>` and
   `${PREFIX}/lib*/qore-modules/<ver>`)
4. **Per-Program `appended` paths** (in the order they were added)

The `%prepend` / `%append` lists live on the `QoreProgram` and inherit
to subprograms that share the parent's program tree (see
[Subprogram propagation](#subprogram-propagation) below).

### Variable interpolation

Expansion happens **at parse time, on the parsing host** — not at AOT
runtime, not at `load_module()` time.  This matters because:

- The expanded path becomes part of the persisted Program state
  (and is serialised into AOT artifacts).
- Macros like `${SCRIPT_DIR}` MUST refer to the script being parsed
  on the parsing host, not the host that loads the AOT artifact.
- For env vars: the env at parse time is what's substituted.  AOT
  binaries that depend on `${OMQ_DIR}` therefore need OMQ_DIR set
  at COMPILE time, not at runtime — which is fine because the AOT
  output is for that deployment.

If you want late binding to runtime env, use the legacy
`QORE_MODULE_DIR` env var instead of `%prepend-module-path` (the two
mechanisms compose — the env var still takes effect at level 2 of the
search-path stack).

#### Predefined macros

| Macro              | Value at parse time                                            |
| ------------------ | -------------------------------------------------------------- |
| `${SCRIPT_DIR}`    | absolute directory of the file containing the directive        |
| `${SCRIPT_NAME}`   | basename of the file containing the directive                  |
| `${SCRIPT_PATH}`   | absolute path of the file containing the directive             |
| `${PROGRAM_DIR}`   | absolute directory of the **top-level** program file           |
| `${QORE_VERSION}`  | libqore version string (e.g. `2.3.0`)                          |
| `${QORE_PREFIX}`   | libqore install prefix (e.g. `/usr`)                           |
| `${QORE_MODULE_VERSION}` | module API version (e.g. `2.0`) — useful for vendored module dirs |

`${SCRIPT_*}` always resolves against the file the directive
literally appears in; `${PROGRAM_DIR}` is useful for module files
(`.qm`, `.qc`) that want to reference the top-level program's
location, not their own.

For files parsed from in-memory buffers (no on-disk file, e.g.
`Program::parse(string)`), `${SCRIPT_*}` macros raise a parse error.
Callers that want this to work should use `Program::parseFile()` or
explicitly set `QoreProgram::setScriptPath()` before parse.

#### Environment fallback

Anything not in the predefined-macro table is looked up in the
process environment.  No interpretation of leading dots, no
`PATH`-style colon splitting on the macro name — `${OMQ_DIR}` reads
the environment variable named `OMQ_DIR` literally.

#### Escape syntax

`\$` inside the quoted path is a literal `$` (not the start of a
macro reference).  This is a minor concession; the pattern is
expected to be rare in real paths.

#### Error cases

- Unknown macro / unset env var: parse error, "undefined variable
  `NAME` in path argument to %prepend-module-path".
- Unterminated `${`: parse error, "expected `}` to close variable
  reference".
- Empty resulting path: parse error, "empty path computed from
  variable expansion".

### Subprogram propagation

When a parent Program creates a subprogram (via `Program::new()` or
`Program::createProgram()`), the subprogram **inherits the parent's
prepend/append lists**.  This matches the inheritance behaviour of
parse options.

Subprograms can also issue their own `%prepend-module-path` /
`%append-module-path` directives, which extend (don't replace) the
inherited list.

`PO_NEW_PROGRAM_DIR` (a new parse option, see
[New parse option](#new-parse-option)) opts a subprogram OUT of
inheritance — it starts with an empty prepend/append list.  Useful
for sandboxed subprograms that should only load from their own
explicitly declared paths.

### Runtime `load_module()`

Runtime module loads via the `Program::loadModule()` /
`Program::loadApplyToUserModule()` API and the eponymous
`load_module()` builtin function consult the same per-Program
prepend/append lists at load time.  Without this, a script could
`%prepend-module-path` for parse-time `%requires` resolution but
runtime loads would still hit the system default path — surprising
and inconsistent.

The lookup order at runtime exactly mirrors the parse-time order
listed under [Search-path layering](#search-path-layering).

### Sandboxing

The directive itself is parse-time-only — no runtime cost, no I/O at
the directive site.  The `%requires` (or runtime `load_module()`)
that subsequently uses the path still goes through the standard
sandbox gate (`PO_NO_FILESYSTEM`, `PO_NO_LOCALE_CONTROL`, etc.), so
no new attack surface is introduced beyond what `%requires` already
implies.

A caller embedding Qore from C++ that wants to **prevent** programs
from extending their own search path can set the new parse option
`PO_NO_MODULE_PATH_DIRECTIVES`.  Under this option,
`%prepend-module-path` / `%append-module-path` raise a parse error.
This composes with `PO_NEW_STYLE` / `PO_REQUIRE_TYPES` / etc.

## AOT integration

The expanded path lists are stored on `qore_program_private` in two
new vectors:

```cpp
std::vector<std::string> prepended_module_paths;
std::vector<std::string> appended_module_paths;
```

The AOT writer (`QoreAOTBinary::serializeProgram` /
`writeProgramOptions`) emits them as two new sections:

- `MODULE_PATH_PREPEND` — count + list of strings
- `MODULE_PATH_APPEND`  — count + list of strings

A new feature flag `QORE_AOT_FEAT_MODULE_PATH_LISTS = 1ULL << <next>`
gates the format change; older `.qmod` blobs without the bit
deserialise to empty lists (backward compatible).

The AOT reader (`QoreAOTBinaryDeserializer::deserializeShells`)
**re-applies** the lists to the target Program before any of the
blob's `%requires`-equivalent dependency loads run.  This means an
AOT binary's bundled module dependencies get found via the same
prepend/append paths the source program used — without OMQ_DIR or
any other env var being set at runtime.

For multi-blob batches (`QoreAOTBinaryMultiDeserializer`), the per-blob
lists are merged and de-duplicated into the target Program's lists
before phase 2 (`resolveAll`) runs.

## New parse option

```cpp
PO_NO_MODULE_PATH_DIRECTIVES = 1ULL << <next>
```

When set, `%prepend-module-path` and `%append-module-path` raise
a parse error.  Default: NOT set (directives allowed).
`%modern` does NOT enable this — modern scripts that legitimately
want to vendor modules should be able to do so.

## Migration path for Qorus

1. Land the directive in libqore.
2. Replace `qorus_setup_module_paths()` with a top-of-file directive
   in each Qorus binary's entrypoint script:

   ```qore
   %prepend-module-path "${OMQ_DIR}/lib/modules"
   %prepend-module-path "${OMQ_DIR}/qlib"
   %prepend-module-path "${OMQ_DIR}/user/modules"
   ```

3. Once all binaries are converted, delete `qorus_setup_module_paths()`.
   AOT-compiled Qorus binaries will then resolve their own modules
   without needing an env-var hack or a C++ entrypoint shim.

The legacy `QORE_MODULE_DIR` env var continues to work — it sits at
level 2 of the search-path stack, so existing deployments that depend
on it remain unaffected.

## Open questions

1. **Multi-line / list form** — should we also support
   `%prepend-module-path "p1", "p2", "p3"` as one directive?  Argument
   for: matches `%try-module` and reduces line count.  Argument
   against: harder to read, no real win over three separate directives.
   **Default: no, single-arg only.**

2. **Idempotency / dedup** — if the same path is added twice (e.g.,
   inherited from parent + re-issued in subprogram), do we
   silently dedup or list it twice?  Functional impact is nil
   (ModuleManager would just check the same dir twice).  **Default:
   silent dedup at insert time.**

3. **`${SCRIPT_DIR}` for buffer-parsed code** — currently proposed as
   a parse error.  Alternative: fall back to `getcwd()`.  Cwd-based
   resolution is brittle, but failing the parse is a sharp edge for
   use cases like `Program::parse(stdin_contents)`.  **Default: parse
   error; user can `setScriptPath()` first if they want it.**

4. **Order of macro / env precedence** — proposal is "macros win on
   conflict".  Alternative: env always wins (so users can override
   built-in macros via env).  Macros-win is safer (predictable) but
   less flexible.  **Default: macros win.**

5. **Pre-existing `addModuleDir` API (C++)** — `MM.addModuleDir()`
   today writes into a process-global list.  Per-Program lists are
   new.  Should we deprecate the global API?  **Default: keep both;
   global remains for backward compat with C++ embedders that don't
   want per-Program isolation.**

6. **Wildcard expansion in paths** — `%prepend-module-path
   "${OMQ_DIR}/qlib/*"` to glob-expand at parse time.  Argument for:
   matches what cmake `file(GLOB)` users expect.  Argument against:
   adds glob dependency, makes errors harder to attribute, slower
   parse.  **Default: out of scope; revisit if a real use case
   appears.**
