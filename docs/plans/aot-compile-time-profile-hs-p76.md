## Implications for the roadmap

This trace fundamentally changes the phase priorities from the original
`aot-compile-time-optimization-roadmap.md`:

### Phase 3 (parallel codegen) hits Amdahl's wall

Even with perfect N-way parallelism across 16 cores, the wall-clock
floor is the serial critical path — **handleRequest at 533s**.
Parallelism would reduce the other 79s to near-zero but leave
handleRequest untouched. Target: **~533s**, not the hoped-for ~100s.

### Phase 5 (outlining) is NOW the top-priority lever

If `handleRequest` is outlined into ~10 helper functions of similar
complexity, each helper compiles in ~50s. Combined with Phase 3
parallelism (16 cores), wall-clock drops to ~50s (compile time of the
biggest helper). Combined target: **~50-100s**, which hits the 120s
goal.

### Phase 2 (caching) still valuable for dev cycles

If an edit touches only function X, only X recompiles. For HS:
- Edit a 0.1s function: 0.1s rebuild.
- Edit sendReply (57s): 57s rebuild.
- Edit handleRequest (533s): 533s rebuild. **Unchanged by caching.**

Caching is a clear win for "edit small function" flows, but
handleRequest itself is the ceiling when it changes. Outlining reduces
the ceiling.

### Revised phase order

1. **Phase 1** — DONE (this profile).
2. **Phase 5 (outlining)** — HIGHEST PRIORITY. Target: split
   handleRequest (and sendReply) into ≥5 functions each. Reduces the
   handleRequest ceiling from 533s to ~50s per helper.
3. **Phase 2 (caching)** — dev-cycle win. Composable with Phase 5: if a
   handleRequest helper changes, only that helper recompiles.
4. **Phase 3 (parallelism)** — now meaningful. With helpers at ≤50s
   each, parallelism closes the wall-clock toward 50s + overhead.
5. **Phase 4 (.qo)** — independent, separate track.
6. **Phases 6-7** — optional polish.

## What causes handleRequest to be so expensive?

Hypotheses (need instrumentation to confirm):
- Huge number of basic blocks (try/catch per connection, per-request
  dispatch, many branches).
- Deeply nested conditionals blowing up LLVM's MachineInstr graph.
- LLVM SelectionDAG's quadratic behavior on function size.
- Register allocator pressure on so many live intermediates.

To diagnose:
- `QORE_DUMP_IR_AFTER_OPT=1` → inspect the IR for handleRequest.
- `llc --time-passes` on the extracted function → per-backend-pass
  breakdown.

## Outlining approach (preview)

In Qore IR generation (lib/QoreIRBuilder.cpp or similar), detect
functions exceeding a threshold (e.g., 300 IR BBs). For each large
function:

1. Identify natural boundaries: try-catch bodies, switch arms, loop
   bodies with ≥K BBs.
2. Extract each boundary's content into its own helper function.
3. Replace the original code with a call to the helper.
4. Preserve Qore semantics: shared locals passed by reference or
   captured, exception scoping intact.

Validation: runtime benchmark to ensure the extra indirection doesn't
cost more than ~3%.
